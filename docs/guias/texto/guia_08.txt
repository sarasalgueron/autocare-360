4. useEffect: modelo mental correcto
Un Effect se usa para sincronizar un componente con algo externo a React: red, navegador, suscripciones, timers o librerias externas. No debe usarse para calcular valores que pueden obtenerse directamente durante el render.
Anatomia conceptual de un Effect
useEffect(() => {
  // 1. setup: sincronizar con el sistema externo

  return () => {
    // 2. cleanup: detener/deshacer la sincronizacion anterior
  };
}, [dependencias]);

Situacion
Effect?
Razon
GET inicial al backend
Si
Sincroniza la UI con un sistema externo.
Escuchar online/offline del navegador
Si
Suscripcion externa que requiere cleanup.
Filtrar un array ya cargado
No
Es una transformacion pura derivable durante render.
Responder a click Guardar
No para iniciar el POST
El evento del usuario ya indica cuando ejecutar la accion.
Cambiar document.title por una seleccion
Si
Sincroniza con una API externa del navegador.

5. Dependencias: por que el Effect se repite
Effect dependiente de clienteId
useEffect(() => {
  const controller = new AbortController();

  void clienteService
    .obtenerPorId(clienteId, controller.signal)
    .then(setCliente)
    .catch((error) => {
      if (!(error instanceof DOMException && error.name === 'AbortError')) {
        setError('No se pudo cargar el cliente');
      }
    });

  return () => controller.abort();
}, [clienteId]);

Cuando clienteId cambia, React ejecuta primero el cleanup del Effect anterior y luego el nuevo setup.
No se deben eliminar dependencias solo para silenciar el linter.
Una dependencia debe aparecer cuando el Effect lee un valor reactivo definido en el componente.
Funciones u objetos creados en cada render pueden provocar ejecuciones adicionales si se usan como dependencias.
6. Cleanup + AbortController
AbortController permite asociar una señal a fetch. Al invocar abort(), la operacion puede cancelarse y fetch rechaza con un AbortError. Esto evita continuar trabajo que ya no es necesario.
shared/utils/isAbortError.ts
export function isAbortError(error: unknown): boolean {
  return error instanceof DOMException && error.name === 'AbortError';
}

Carga cancelable
useEffect(() => {
  const controller = new AbortController();

  const load = async () => {
    try {
      setLoading(true);
      setError('');
      const data = await clienteService.listar(controller.signal);
      setClientes(data);
    } catch (error) {
      if (!isAbortError(error)) {
        setError(error instanceof Error ? error.message : 'Error de carga');
      }
    } finally {
      if (!controller.signal.aborted) {
        setLoading(false);
      }
    }
  };

  void load();
  return () => controller.abort();
}, []);

Importante: Abortar una peticion porque el componente se desmonta o cambia de recurso no debe mostrarse al usuario como "error del sistema". AbortError es una cancelacion esperada.

7. Respuestas obsoletas y condiciones de carrera
Una condicion de carrera aparece cuando varias operaciones asincronas compiten y una respuesta antigua termina sobrescribiendo datos mas nuevos. Es especialmente visible en busquedas, detalle por id o filtros que disparan requests.
Abortar + ignorar resultados que ya no corresponden
useEffect(() => {
  const controller = new AbortController();
  let ignore = false;

  const load = async () => {
    try {
      setLoading(true);
      const data = await clienteService.obtenerPorId(
        clienteId,
        controller.signal,
      );

      if (!ignore) setCliente(data);
    } catch (error) {
      if (!ignore && !isAbortError(error)) {
        setError('No se pudo cargar el cliente');
      }
    } finally {
      if (!ignore) setLoading(false);
    }
  };

  void load();

  return () => {
    ignore = true;
    controller.abort();
  };
}, [clienteId]);

Dos defensas: AbortController intenta detener el request. La bandera ignore evita aplicar una respuesta que ya no corresponde, incluso si existe trabajo asincrono posterior que no pudo abortarse.

8. StrictMode y el Effect que "se ejecuta dos veces"
En desarrollo, StrictMode realiza comprobaciones adicionales. Entre ellas puede ejecutar un ciclo extra setup -> cleanup -> setup para ayudar a detectar Effects sin limpieza correcta. Ese comportamiento no ocurre de la misma forma en el build de produccion.
Respuesta incorrecta
Respuesta profesional
"Quito StrictMode para que deje de duplicar"
Primero comprobar si el Effect soporta setup/cleanup/setup correctamente.
"Uso useRef para impedir la segunda ejecucion"
No esconder el problema; implementar cleanup y hacer el Effect repetible.
"React esta enviando doble POST"
Los POST iniciados por clicks deben vivir en handlers, no en un Effect de montaje.

10. Custom Hooks: reutilizar logica, no compartir estado
Un custom Hook puede contener useState, useEffect y otros Hooks. Su nombre debe comenzar por use. Dos componentes que llaman al mismo custom Hook reutilizan la logica, pero cada llamada conserva su propio estado.
Buen nombre
Intencion
useClientes
Gestionar la logica de datos de Clientes.
useVehiculos
Gestionar la logica de datos de Vehiculos.
useAsyncList
Patron generico para cargar una coleccion asincrona.
useMount
Evitar: intenta esconder semantica de Effect.

11. Implementar useAsyncList<T>
shared/hooks/useAsyncList.ts
import { useCallback, useEffect, useState } from 'react';
import { isAbortError } from '../utils/isAbortError';

type Loader<T> = (signal: AbortSignal) => Promise<T[]>;

export function useAsyncList<T>(loader: Loader<T>) {
  const [data, setData] = useState<T[]>([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState('');
  const [reloadToken, setReloadToken] = useState(0);

  const reload = useCallback(() => {
    setReloadToken((value) => value + 1);
  }, []);

  useEffect(() => {
    const controller = new AbortController();

    const load = async () => {
      try {
        setLoading(true);
        setError('');
        const result = await loader(controller.signal);
        setData(result);
      } catch (error) {
        if (!isAbortError(error)) {
          setError(
            error instanceof Error ? error.message : 'Error de carga',
          );
        }
      } finally {
        if (!controller.signal.aborted) setLoading(false);
      }
    };

    void load();
    return () => controller.abort();
  }, [loader, reloadToken]);

  return { data, setData, loading, error, setError, reload };
}

Contrato del loader: El loader debe ser una referencia estable. Los metodos clienteService.listar y vehiculoService.listar definidos fuera del componente cumplen este objetivo. Si se crea una funcion nueva en cada render, el Effect podria repetirse innecesariamente.

12. Hooks de dominio: useClientes y useVehiculos
features/clientes/hooks/useClientes.ts
import { clienteService } from '../services/clienteService';
import { useAsyncList } from '../../../shared/hooks/useAsyncList';
import type { Cliente } from '../models/Cliente';

export function useClientes() {
  return useAsyncList<Cliente>(clienteService.listar);
}

features/vehiculos/hooks/useVehiculos.ts
import { vehiculoService } from '../services/vehiculoService';
import { useAsyncList } from '../../../shared/hooks/useAsyncList';
import type { Vehiculo } from '../models/Vehiculo';

export function useVehiculos() {
  return useAsyncList<Vehiculo>(vehiculoService.listar);
}

Responsabilidad: useAsyncList conoce el patron asincrono generico; useClientes/useVehiculos expresan la intencion del dominio. Los services siguen siendo los unicos que conocen las rutas HTTP.

13. Refactor de ClientesPage y VehiculosPage
ClientesPage.tsx - consume el Hook
const {
  data: clientes,
  setData: setClientes,
  loading,
  error,
  setError,
  reload,

const handleSaved = (saved: Cliente, mode: 'create' | 'edit') => {
  setClientes((prev) =>
    mode === 'create'
      ? [...prev, saved]
      : prev.map((item) => item.id === saved.id ? saved : item),

14. Mensajes de exito sin mezclar responsabilidades
Mensaje simple de confirmacion
const [successMessage, setSuccessMessage] = useState('');

const showSuccess = (message: string) => {
  setSuccessMessage(message);
  window.setTimeout(() => setSuccessMessage(''), 2500);
};

// despues de un POST exitoso
showSuccess('Cliente creado correctamente');

Escalabilidad: Para una aplicacion mas grande conviene un sistema de toasts reutilizable. En esta guia basta separar successMessage de error para que el estudiante no use un unico string ambiguo.

17. Mapa de responsabilidades final
Pieza
Responsabilidad

Coordina seleccion, edicion, filtros, formularios, tablas y mutaciones.
Custom Hook
Gestiona estado/effect reutilizable de carga y ciclo asincrono.
Service
Define operaciones HTTP y usa apiClient.
apiClient
URL base, headers, parseo y errores HTTP comunes.

Estado temporal, validacion, submit y UX del formulario.

Persistencia e integridad referencial.

Flujo de carga: Render -> custom Hook -> useEffect -> service -> apiClient -> fetch -> Spring -> JSON -> setData -> re-render. Si cambia la dependencia o se desmonta: cleanup -> abort.
