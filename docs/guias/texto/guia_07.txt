3. La relacion Cliente 1:N vista desde el frontend
En el dominio, un Cliente puede tener muchos Vehiculos; cada Vehiculo pertenece a un Cliente. En el frontend, la forma mas simple de representar la referencia es conservar el identificador del propietario.
features/vehiculos/models/Vehiculo.ts
export interface Vehiculo {
  id: number;
  placa: string;
  marca: string;
  modelo: string;
  anio: number;
  color: string;
  clienteId: number;
  activo: boolean;
}

Capa
Representacion de la relacion
PostgreSQL
vehiculo.cliente_id referencia a cliente.id mediante FK.
JPA
Vehiculo posee una relacion ManyToOne hacia Cliente o un DTO equivalente.
JSON
Puede exponerse como clienteId o como un objeto cliente, segun el contrato.
React
El formulario controla clienteId y la tabla resuelve el nombre del Cliente.

Idea central: N:M no aparece aqui. Desde Vehiculo, la relacion es muchos Vehiculos -> un Cliente. El selector debe permitir elegir exactamente un propietario.

4. Tipos de formulario y payload
VehiculoFormData vs VehiculoRequest
export interface VehiculoFormData {
  placa: string;
  marca: string;
  modelo: string;
  anio: string;
  color: string;
  clienteId: string;
  activo: boolean;
}

export interface VehiculoRequest {
  placa: string;
  marca: string;
  modelo: string;
  anio: number;
  color: string;
  clienteId: number;
  activo: boolean;
}

Por que string: Un <input> y un <select> controlados manejan value como string de forma natural. El usuario puede tener temporalmente un valor vacio; por eso se valida primero y despues se convierte anio/clienteId con Number(...).

5. vehiculoService: CRUD completo
features/vehiculos/services/vehiculoService.ts
import { apiFetch } from '../../../api/apiClient';
import type { Vehiculo } from '../models/Vehiculo';
import type { VehiculoRequest } from '../types/VehiculoFormData';

export const vehiculoService = {
  listar(signal?: AbortSignal): Promise<Vehiculo[]> {
    return apiFetch<Vehiculo[]>('/vehiculos', { signal });
  },

  obtenerPorId(id: number, signal?: AbortSignal): Promise<Vehiculo> {
    return apiFetch<Vehiculo>(`/vehiculos/${id}`, { signal });
  },

  crear(data: VehiculoRequest): Promise<Vehiculo> {
    return apiFetch<Vehiculo>('/vehiculos', {
      method: 'POST',
      body: JSON.stringify(data),
    });
  },

  actualizar(id: number, data: VehiculoRequest): Promise<Vehiculo> {
    return apiFetch<Vehiculo>(`/vehiculos/${id}`, {
      method: 'PUT',
      body: JSON.stringify(data),
    });
  },

  eliminar(id: number): Promise<void> {
    return apiFetch<void>(`/vehiculos/${id}`, { method: 'DELETE' });
  },
};

Para alimentar el selector de propietario reutilizaremos clienteService.listar(). No duplique un segundo servicio de Clientes dentro de features/vehiculos.
6. Cargar Vehiculos y Clientes
VehiculosPage.tsx - carga inicial
const [vehiculos, setVehiculos] = useState<Vehiculo[]>([]);
const [clientes, setClientes] = useState<Cliente[]>([]);
const [loading, setLoading] = useState(true);
const [error, setError] = useState('');

useEffect(() => {
  const controller = new AbortController();

  const load = async () => {
    try {
      setLoading(true);
      const [vehiculosData, clientesData] = await Promise.all([
        vehiculoService.listar(controller.signal),
        clienteService.listar(controller.signal),
      ]);

      setVehiculos(vehiculosData);
      setClientes(clientesData);
    } catch (err) {
      if (!(err instanceof DOMException && err.name === 'AbortError')) {
        setError(err instanceof Error ? err.message : 'Error al cargar datos');
      }
    } finally {
      if (!controller.signal.aborted) setLoading(false);
    }
  };

  void load();
  return () => controller.abort();
}, []);

Promise.all: Las dos consultas son independientes; pueden ejecutarse en paralelo. Si una falla, en este ejemplo tratamos la carga inicial como fallida y mostramos el error.

8. Validar la relacion antes de construir el payload
Validacion de Vehiculo y propietario
const validarVehiculo = (
  data: VehiculoFormData,
  clientes: Cliente[],
) => {
  const errors: Record<string, string> = {};

  if (!data.placa.trim()) errors.placa = 'La placa es obligatoria';
  if (!data.marca.trim()) errors.marca = 'La marca es obligatoria';

  const anio = Number(data.anio);
  if (!Number.isInteger(anio) || anio < 1900 || anio > 2100) {
    errors.anio = 'Ingrese un anio valido';
  }

  const clienteId = Number(data.clienteId);
  const clienteExiste = clientes.some(
    (cliente) => cliente.id === clienteId && cliente.activo,
  );

  if (!clienteExiste) {
    errors.clienteId = 'Seleccione un cliente valido y activo';
  }

  return errors;
};

Construccion del payload despues de validar
const payload: VehiculoRequest = {
  placa: formData.placa.trim().toUpperCase(),
  marca: formData.marca.trim(),
  modelo: formData.modelo.trim(),
  anio: Number(formData.anio),
  color: formData.color.trim(),
  clienteId: Number(formData.clienteId),
  activo: formData.activo,
};

Seguridad de reglas: Validar en React mejora UX, pero no sustituye la validacion en Spring Boot. El backend debe comprobar que clienteId existe y que la asignacion esta permitida.

12. Sincronizar POST, PUT y DELETE
VehiculosPage.tsx - sincronizacion
const handleSaved = (saved: Vehiculo, mode: 'create' | 'edit') => {
  setVehiculos((prev) =>
    mode === 'create'
      ? [...prev, saved]
      : prev.map((item) => item.id === saved.id ? saved : item),
  );
  setEditingVehiculo(null);
};

const handleDelete = async (vehiculo: Vehiculo) => {
  if (!window.confirm(`¿Eliminar el vehiculo ${vehiculo.placa}?`)) return;

  try {
    setDeletingId(vehiculo.id);
    setError('');
    await vehiculoService.eliminar(vehiculo.id);
    setVehiculos((prev) => prev.filter((v) => v.id !== vehiculo.id));
    if (editingVehiculo?.id === vehiculo.id) setEditingVehiculo(null);
  } catch (err) {
    setError(err instanceof Error ? err.message : 'No se pudo eliminar');
  } finally {
    setDeletingId(null);
  }
};

Regla: La UI solo cambia despues de una respuesta exitosa. Si el backend rechaza la placa, el cliente o el DELETE, conserve los datos y muestre el error.

13. Estructura final de VehiculosPage
VehiculosPage.tsx - integracion
export default function VehiculosPage() {
  const [vehiculos, setVehiculos] = useState<Vehiculo[]>([]);
  const [clientes, setClientes] = useState<Cliente[]>([]);
  const [editingVehiculo, setEditingVehiculo] = useState<Vehiculo | null>(null);
  const [clienteFiltro, setClienteFiltro] = useState('');
  const [deletingId, setDeletingId] = useState<number | null>(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState('');

  // useEffect de carga inicial
  // handleEdit -> GET /vehiculos/{id}
  // handleSaved -> POST/PUT + sincronizacion
  // handleDelete -> DELETE + filter

  const vehiculosVisibles = clienteFiltro === ''
    ? vehiculos
    : vehiculos.filter(
        (v) => v.clienteId === Number(clienteFiltro),
      );

  if (loading) return <div className="state-card">Cargando...</div>;

  return (
    <section className="page-stack">
      <header>
        <h1>Vehiculos</h1>
        <p>CRUD completo + relacion Cliente 1:N.</p>
      </header>

      {error && <div className="state-card error">{error}</div>}

      <VehiculoForm
        clientes={clientes}
        vehiculo={editingVehiculo}
        onSaved={handleSaved}
        onCancelEdit={() => setEditingVehiculo(null)}
      />

      {/* selector clienteFiltro */}

      <VehiculoTable
        vehiculos={vehiculosVisibles}
        clientes={clientes}
        onEdit={handleEdit}
        onDelete={handleDelete}
        deletingId={deletingId}
      />
    </section>
  );
}

15. Flujos que el estudiante debe poder dibujar
Accion
Flujo resumido
Crear Vehiculo
Form -> validar Cliente -> POST -> Controller -> Service valida Cliente -> JPA INSERT con FK -> JSON -> setVehiculos.
Editar propietario
GET/{id} -> form precarga clienteId -> seleccionar otro Cliente -> PUT -> UPDATE cliente_id -> respuesta -> map().
Mostrar propietario
Vehiculos + Clientes -> Map por id -> VehiculoTable muestra nombre sin request por fila.
Filtrar
clienteFiltro -> Number -> filter por clienteId -> re-render sin tocar backend.
Eliminar
Confirm -> DELETE/{id} -> backend -> 204 -> filter; si falla, conservar fila.

Defensa extrema: El estudiante debe identificar claramente que el usuario elige un Cliente por nombre, pero el request persiste una referencia identificada por clienteId.
